---
name: Imported project with pre-existing artifact.toml
description: What to do when a GitHub-imported repo already has artifacts/*/.replit-artifact/artifact.toml files but listArtifacts() returns empty and no workflows exist.
---

A project can be re-imported from GitHub with fully-formed `artifacts/<slug>/.replit-artifact/artifact.toml`
files already committed (from a prior Replit session), yet the platform's artifact registry has no record
of them: `listArtifacts()` returns `[]` and `listWorkflows()` returns `[]`, even though the `.replit` file
itself was freshly regenerated by the importer (it only has generic `[workflows]`/`[agent]`/`[nix]` sections,
no service entries).

**Why:** artifact registration lives in platform state keyed by artifact ID, separate from the files in git.
Right after a GitHub re-import there can be a lag before the platform's importer scans `artifact.toml` files
on disk and (re)registers them — during that window `listArtifacts()`/`listWorkflows()` look empty.

**How to apply:** Don't rush to work around it by hand. Confirmed sequence: `createArtifact()` with the same
slug fails fast with `ARTIFACT_DIR_EXISTS` (safe, non-destructive, but a dead end — it does not adopt existing
files). As a stop-gap, manually registering plain `configureWorkflow` workflows that bind the same ports the
artifact.toml declares gets the app running immediately, but shortly after, the platform can catch up on its
own and auto-register the real `artifacts/<slug>: <service>` workflows — which then collide on the same ports
(`EADDRINUSE`) with the manual ones and both fail. If that happens: `removeWorkflow` the manual ones, then
check for orphaned processes still holding the ports with `ps aux` / `cat /proc/<pid>/cwd` (removing a
manually-configured workflow does not always reap its child process tree) and `kill -9` them before
restarting the real artifact-managed workflows.

Practical guidance for next time: after an import where `listArtifacts()` is unexpectedly empty despite
`artifact.toml` files existing, prefer re-checking `listArtifacts()`/`listWorkflows()` again after a short
delay (e.g. after finishing unrelated setup steps like `pnpm install`/db push) before reaching for the manual
`configureWorkflow` workaround — it may resolve on its own and save a cleanup pass.
